## 1. Accelerator architecture
**Required by:** Deliverable "accelerator architecture"; Instruction 1 "clearly describe the datapath, control FSM, memory/buffer organization, window generation"; Instruction 4 "state all assumptions clearly"; spec items 1, 3, 5 (image size, programmable kernel, stride 1).
**Say:**
- Function (REQUIRED, items 1/3/5): 3x3 same (zero-padded) convolution over a 32x32 grayscale image, stride 1, 1024 input pixels in, 1024 output pixels out, one output pixel per clock.
- Precision at a glance (details in section 7): input 8-bit unsigned Q8.0; coefficients 8-bit signed integer Q8.0 (COEF_FRAC = 0; the package toggle COEF_FRAC = 7 rebuilds for Q1.7); output 16-bit signed, saturating; ReLU is a build-time parameter RELU, default off.
- Programmable kernel (REQUIRED, item 3): 9 coefficients loaded through write_en / write_addr[3:0] / data_write[7:0], write_addr = 3*row + col (0..8), row-major, same order as the taps; addresses 9..15 ignored; writes ignored while busy; reloadable between frames (proven by the back-to-back run, sobel_x then sharpen, kernel swapped while frame 1 drains).
- Architecture type (reuse the exact phrase in Table 1): streaming line-buffer sliding-window convolution, fully parallel 9-multiplier datapath, 3 pipeline register stages after the window, 1.0 output pixel per cycle.
- The architectural claim: strict control/datapath split. control_fsm (rtl/control_unit.sv) owns every counter and flag: state, in_cnt (10b), out_r/out_c (5b each), drain_cnt (6b), four registered edge flags. window_gen, line_buffer, coeff_reg, mult8x8 and the adder tree hold no position state; window_gen has no counters and no valid output.
- Control-to-datapath signals are only: en and the four edge flags into window_gen, busy into coeff_reg (write lock), win_valid into the 3-stage valid chain.
- Datapath in one line: 9 taps (9x8b) x 9 coefficients (9x8b) -> 9 LUT multipliers -> stage-1 register prod_r 9x16b -> three 3-input row adders -> stage-2 register row_r 3x18b -> one 3-input 20-bit adder -> saturate 20b->16b -> ReLU mux -> stage-3 register pixel_out.
- Valid chain runs level with the data: win_valid -> v_prod -> v_row -> valid_out; pipeline registers are free-running, so a valid_in stall becomes a bubble in valid_out exactly 3 cycles later, never corruption.
- Window generation: two 32-deep 8-bit line buffers in series (LB0 from input_in, LB1 from LB0) + 9 tap registers a..i + combinational zero-pad masks driven by the edge flags (section 6).
- Frame sequence: IDLE -> FILL (34 consume-only cycles) -> STREAM (consume + output until the 1024th pixel is consumed) -> DRAIN (34 output-only cycles, en forced high, input ignored) -> DONE (1 cycle, frame_done) -> IDLE. en = valid_in except DRAIN (1) and DONE (0). Consume-only cycles equal output-only cycles (34 = 34) so inputs and outputs both total 1024.
- Interface, 42 pins: clk, rst_n (active-low, synchronous, every module), input_in[7:0] + valid_in, write port 13 pins (write_en, write_addr[3:0], data_write[7:0]), pixel_out[15:0] signed + valid_out, busy. 1 + 1 + 8 + 1 + 13 + 16 + 1 + 1 = 42.
- Flow control: no ready signal. valid_in may drop on any cycle; en gates line buffers, taps and counters together (the window freezes coherently). Source-side frame gating: the source streams exactly 1024 pixels per frame and holds the next frame until busy falls. busy = not IDLE and not DONE; it falls 3 cycles before the last valid_out because the last window is already in the pipeline.
- Latency 37 cycles from first accepted pixel to first valid_out = 34 window fill + 3 pipeline stages. Throughput 1.0 output pixel/cycle peak, gapless within a frame; 1024 outputs in 1061 cycles = 0.965 sustained per frame including fill and drain.
- FoM lever 1 (REQUIRED rationale), throughput = 1 px/cycle: 9 parallel multipliers consume all 9 window pixels every cycle. The 3-multiplier / one-output-per-3-cycles alternative was rejected: throughput x3 for a denominator the pre-implementation estimate put at roughly 1.5x (docs/ARCHITECTURE_LOCKED.md section 4; label it an estimate, not a measurement). It also claims the named bonus.
- FoM lever 2, 0 BRAM (100x penalty per tile): the line buffers are fabric shift registers, inferred as 16 SRLC32E = 16 LUTs for both. Even the cheapest block-RAM mapping (one tile, 100 LUT-equivalents) would raise the denominator from 879 to 879 - 16 + 100 = 963 (arithmetic, +9.6%).
- FoM lever 3, 0 DSP (50x penalty each): use_dsp = "no" attribute on mult8x8 (rtl/multiplier.sv) plus -max_dsp 0 in fpga/build.tcl; the nine 8u x 8s multipliers cost 52-59 LUTs each, 496 in total. Frame this honestly: 9 DSP48E1 would count 450 against 496 LUTs, so the choice is near-neutral on the denominator; it is kept because an 8x8 product uses a fraction of a 25x18 DSP48E1, keeps the whole design in one fabric type with one power model, and keeps the RTL vendor-neutral (one attribute).
- Where the 879 LUTs sit (routed, indicative because Vivado combines LUTs across hierarchy boundaries): 9 multipliers 496, window_gen 132 (116 logic + 16 SRL), coeff_reg 120, control_fsm 80, top-level adder tree / saturate / ReLU 90. DSPs and BRAMs are already 0, so every remaining FoM point is a LUT.
- Constant-coefficient multipliers were rejected: all shipped kernels use only 0, +-1, +-2, +-4, 5 and hardcoding would save roughly 300 LUTs, but forfeits mandatory programmability (item 3).
- Headline results, forward-referenced to sections 12-14: xc7z020clg400-1 (PYNQ-Z2, TUL), Vivado 2025.2, 125 MHz constraint (8.000 ns); 879 LUTs, 441 FFs, 0 DSP, 0 BRAM, 42 IOB, 1 BUFG; WNS +0.742 ns, WHS +0.153 ns, 0 failing endpoints of 602, Fmax 137.8 MHz; total power 0.158 W (0.107 static + 0.052 dynamic, SAIF-annotated, Medium confidence); FoM = 1.0 / (0.158 x 879) = 7.20e-3 at 125 MHz.
- Verification headline, forward-referenced to sections 9-11: golden_model/golden.py (numpy); 22 regression runs all pass (7 kernels x clean / fixed stalls / random stalls + one back-to-back run), RELU=0 and RELU=1 DUTs on the same stimulus; hw_out/ 14 files byte-identical to golden_model/hex/.
- Module/file map: rtl/cnn_pkg.sv (parameters), rtl/control_unit.sv (module control_fsm), rtl/window_gen.sv, rtl/line_buffer.sv, rtl/coeff_reg.sv, rtl/multiplier.sv (module mult8x8), rtl/top.sv (instantiation, 9 multipliers, adder tree, saturate, ReLU, three pipeline registers, valid chain).
- Bonuses claimed by this architecture: one-output-pixel-per-cycle pipelined; multiple kernels (programmable, 5 real kernels verified, reload between frames); ReLU (parameter, verified on all 7 kernels); edge-detection demo in simulation rendered from hw_out/. Board demo not claimed (fpga/top.bit exists for the real PYNQ-Z2 pinout; the pixel-source wrapper was not built).

## 5. Memory organization
**Required by:** Deliverable "memory organization"; Instruction 1 "memory/buffer organization"; spec item 9 "BRAMs" in the implementation results; the FoM's 100 x BRAMs term.
**Say:**
- (REQUIRED, item 9) Block RAM used: 0 of 140 tiles (RAMB36 0, RAMB18 0); LUT as Distributed RAM: 0; the only memory-class primitive in the whole design is 16 x SRLC32E (LUT as Shift Register 16). fpga/reports/utilization.rpt sections 1 and 3.
- The image is never stored. State on chip at any time is 2 rows + 9 pixels: two 32-deep line buffers (2 x 32 x 8 = 512 bits) and nine 8-bit tap registers (72 bits). One external read per output pixel; the 9 window pixels come from internal registers, nothing is re-read.
- Line buffer (rtl/line_buffer.sv): a DEPTH x WIDTH = 32 x 8 shift register, en-gated, synchronous reset; sr[0] takes d_in, d_out = sr[DEPTH-1]. No write pointer, no read pointer, no address compare - the delay is fixed by the structure.
- Why it infers as SRL despite the synchronous reset: nothing reads an intermediate element, only sr[DEPTH-1], so Vivado maps the chain into LUT shift registers (fpga/reports/RESULTS.md, "Line buffers came out as SRLs"). 16 LUTs instead of 512 flip-flops.
- Evidence, synth.log "Static Shift Register Report": two rows, u_wg/LB1/sr_reg[0][7] and u_wg/tap_reg_reg[2][7], each Length 30, Width 8, SRLC32E 8 - 16 SRLC32E in total; "Report Cell Usage" lists SRLC32E 16; utilization.rpt "LUT as Shift Register 16" and utilization_hier.rpt u_wg SRLs 16 agree.
- Reading that table for a judge: an SRLC32E is a single LUT6 used as a 32-bit shift register, so 8 cells carry one 8-bit-wide line; the "Pull out last Reg = YES" column shows Vivado kept the reset-bearing end stage as an ordinary flip-flop and put the other 30 stages of each chain in SRLs. Quote the 16 LUTs; do not over-specify beyond what the table says.
- Depth 32 exactly matches the primitive: SRLC32E is 32 deep, so a 32-pixel image row costs precisely one LUT per bit; a 29-deep buffer would cost the same 8 LUTs per line and buy nothing.
- The 100x argument (REQUIRED for the FoM story): one block RAM tile counts as 100 LUT-equivalents; both line buffers together cost 16 LUTs. The cheapest BRAM mapping (one tile for both) would make the denominator 879 - 16 + 100 = 963, +9.6% (arithmetic), and would also need write/read address counters, an output register and read-latency alignment that the fixed-depth shift register does not have. A 32 x 8 line is 256 bits, 1.4% of an 18 kbit tile.
- Tap registers: 9 x 8 bits = 72 FFs in window_gen, en-gated, shifted along each row (a<-b<-c, d<-e<-f, g<-h<-i); all 9 are read in parallel every cycle by the multipliers, so they cannot be a RAM of any kind.
- Coefficient registers (rtl/coeff_reg.sv): 9 x 8 bits = 72 FFs; single write port (write_en, write_addr[3:0], data_write[7:0]), guarded by write_en && !busy && write_addr < 9; 9 parallel read buses, no read mux; the multipliers see all 9 coefficients every cycle. Routed cost 120 LUTs (indicative) - that is the write-address decode fanning out to 9 byte-wide enables, not storage.
- Pipeline registers (rtl/top.sv), free-running (no enable): prod_r 9 x 16 = 144 FFs, row_r 3 x 18 = 54 FFs, pixel_out 16 FFs, valid chain v_prod / v_row / valid_out 3 FFs = 217 FFs, matching the top-level row of utilization_hier.rpt.
- Control state (rtl/control_unit.sv): in_cnt 10 + out_r 5 + out_c 5 + drain_cnt 6 + 4 edge flags + state = 35 FFs routed (Vivado re-encoded the 3-bit enum one-hot, see fpga/reports/RESULTS.md).
- Totals: 441 FFs routed = 217 (top-level pipeline) + 72 (coeff_reg) + 35 (control_fsm) + 117 (window_gen, includes the 72 taps); datapath storage 512 + 72 + 72 = 656 bits; BRAM 0; distributed RAM 0.
- Two kinds of enable, deliberately: everything that holds window position or window data (line buffers, taps, counters) is gated by en so a stall freezes the window coherently; everything downstream of the window is free-running and protected by the travelling valid bit. Unique control sets: 16 (utilization.rpt).
- Reset: every register in every module clears on synchronous rst_n. Correct borders do not depend on it - the zero-pad masks do that (section 6, back-to-back run).
- Scaling note for the tradeoffs section: the on-chip state grows with image width only (2 x IMG_W x 8 bits), never with height; larger widths would cascade SRLC32E cells rather than move to block RAM.

## 6. Line-buffer or window-generation method
**Required by:** Deliverable "line-buffer or window-generation method"; Instruction 1 "window generation"; spec item 1 (32x32) and item 5 (stride 1); Instruction 2 (verified against golden vectors).
**Say:**
- (REQUIRED) Structure (rtl/window_gen.sv): input_in feeds tap i and line buffer LB0; LB0's output (in_f) feeds tap f and line buffer LB1; LB1's output (in_c) feeds tap c. Each tap row is a 3-register shift chain: c->b->a, f->e->d, i->h->g. All of it is en-gated; window_gen has no counters and produces no valid.
- Delay of each tap behind input_in, in enabled cycles: i 1, h 2, g 3 (bottom row, from input_in); f 33, e 34, d 35 (middle row, from LB0); c 65, b 66, a 67 (top row, from LB1). Row-to-row spacing is exactly 32 = IMG_W, column spacing exactly 1: the three rows are vertically aligned, the window is a true 3x3.
- When the centre e holds pixel (r, c), the taps hold: a (r-1,c-1) b (r-1,c) c (r-1,c+1) / d (r,c-1) e (r,c) f (r,c+1) / g (r+1,c-1) h (r+1,c) i (r+1,c+1). The window for (r, c) is at the taps once pixel (r+1, c+1) has entered.
- Stride 1 falls out of the structure: one enabled shift moves the window one column; the raster order of the input is the raster order of the output.
- Why depth 32 and not 29 (REQUIRED, the number a reviewer will question): the line buffer carries one full row of vertical delay. The horizontal tap chains hang off the buffer outputs as parallel branches (input_in also feeds LB0; in_f also feeds LB1), so they add no delay along the vertical axis. With 29 the middle row would sit 29 pixels behind the bottom row, a skewed parallelogram that fails the golden diff on every interior pixel (verified by sweep, docs/ARCHITECTURE_LOCKED.md section 7). IMG_W - 3 = 29 belongs only to a topology with the taps inside the delay chain, and since an SRLC32E is 32 deep either way it would not save a LUT.
- Fill latency 34 = 32 + 2 (FILL_CYCLES = LB_DEPTH + 2 in rtl/cnn_pkg.sv): pixel (0,0) enters tap i on shift 1, leaves LB0 after 32 more shifts into tap f on shift 33, and moves f->e on shift 34. So output (0,0) is at the taps on enabled cycle 34, then one new window per enabled cycle for all 1024 positions.
- Only one line buffer sits between the input and the centre tap. LB1 feeds the top row only, and the top row is zero-masked on output row 0, so the first window does not wait the 66 cycles the top row would need. This is why fill is 34 and not 66.
- Zero padding (same convolution) is done by combinational masks after the tap registers, never by writing zeros into the buffers: top_edge -> taps 0,1,2 (a b c); bottom_edge -> 6,7,8 (g h i); left_edge -> 0,3,6 (a d g); right_edge -> 2,5,8 (c f i). Sequential ifs give OR behaviour, so a corner tap is zeroed by either flag; tap 4 (e, the centre) is never touched.
- Coverage of the masks: rows 0 and 31 and columns 0 and 31 = 124 border windows of 1024 are masked (3 taps on an edge, 5 taps at a corner); the 900 interior windows pass all 9 taps unchanged.
- The flags come from control_fsm as registers computed one position ahead (nxt_r == 0, nxt_r == 31, nxt_c == 0, nxt_c == 31, rtl/control_unit.sv), so on every cycle the flag and the window at the taps belong to the same output position. Registering them moved the comparator out of the multiplier path (WNS +0.332 -> +0.742 ns, Fmax 130.4 -> 137.8 MHz, 4 FFs, LUTs 882 -> 879).
- What is left on the critical path is the flag fanout: bottom_edge_reg -> tap zero mux -> multiplier -> prod_r[8][13], 7 logic levels, 7.297 ns, fanout 156, 1.517 ns on that net; all 15 worst paths start at an edge-flag register (detail in section 13).
- Stall behaviour: en low holds LB0, LB1 and all 9 taps; out_adv is low so out_r/out_c and hence the four flags hold; the masked window at the taps is frozen and win_valid is low. A stall is input starvation, never a design bubble.
- Drain behaviour: after the 1024th pixel the FSM forces en high for 34 cycles so the last windows can still shift out; whatever is on input_in during DRAIN enters the bottom tap row, but the only windows whose bottom row contains post-frame data are the row-31 windows (plus tap i of (30,31)), all zero-masked by bottom_edge / right_edge. Proven by hw_out equality on all 7 kernels.
- Back-to-back frames: there is no reset between frames, so when frame 2 starts LB0/LB1 and the taps still hold the tail of frame 1; the row-0 windows of frame 2 carry frame-1 data in taps a b c, and top_edge masks it. The back-to-back regression run (sobel_x then sharpen, 2048 outputs, byte-identical) shows the masks, not the reset, guarantee the border.
- Cost of the window generator (routed, indicative): 132 LUTs = 116 logic (masks and tap-row logic, partly merged into the multipliers' first LUT level by Vivado) + 16 SRL, 117 FFs including the 72 tap bits; 0 BRAM.
- Verification, unit level (tb/tb_window_gen_unit.sv, direct-drives en and the four flags, cycle-accurate shadow model of both line buffers and the nine taps): test 1 ramp of 3 x 32 + 20 = 116 enabled cycles checked every cycle; test 2 en low for 5 cycles, all 9 taps frozen, then one resume shift; test 3 each single edge flag; test 4 the four corner combinations plus an explicit top-left check (taps 0,1,2,3,6 zero, centre not zero). - End-to-end, the window generator is exercised at all 1024 positions by every one of the 22 regression runs and by the byte-identical hw_out/ files (sections 9-11).

## 3. Datapath
**Required by:** Instruction 1 "Clearly describe the datapath ... fixed-point arithmetic"; deliverable "datapath"; bonus "one-output-pixel-per-cycle pipelined architecture"; Table 1 rows "Multipliers / MACs", "Pipeline stages", "Latency", "Throughput".
**Say:**
- Scope: the datapath is everything downstream of the 9 window taps - all in rtl/top.sv except the multiplier cell in rtl/multiplier.sv; it holds no position state (control_fsm owns that) and no feedback loop (pure feed-forward sum tree, not an accumulate-in-place MAC).
- Inputs every cycle: tap_out[0..8] (9 x 8-bit unsigned, already zero-masked by window_gen at borders, row-major a..i) and coef[0..8] (9 x 8-bit signed from coeff_reg, write_addr = 3*row+col, same order as the taps).
- Stage 1 combinational: 9 parallel multipliers 8u x 8s. mult8x8 computes prod = coef * signed'({1'b0, pix}) - the pixel is zero-extended to 9-bit signed so the signed-by-unsigned multiply is exact; Vivado's RTL component statistics list "8x9 Multipliers := 9" (fpga/reports/synth.log).
- Product is 16-bit signed (PROD_W = IN_W + COEF_W = 16), range -32640..+32385.
- Multipliers forced into LUTs: (* use_dsp = "no" *) on mult8x8 plus synth_design -max_dsp 0 in fpga/build.tcl (both, so the result does not depend on one tool default). Result: 0 DSP.
- Multiplier cost: 52 or 59 LUTs each (5 instances at 52, 4 at 59 in fpga/reports/utilization_hier.rpt), 496 LUTs total = 56% of the 879 routed LUTs; per-block split is indicative because Vivado combines LUTs across hierarchy boundaries.
- Stage 1 register: prod_r, 9 x 16 bits, plus v_prod (valid). Synchronous reset, no clock enable, free-running.
- Also inside stage 1's combinational cone, ahead of the multiplier: the tap zero-mask (top -> a,b,c; bottom -> g,h,i; left -> a,d,g; right -> c,f,i) driven by the four REGISTERED edge flags from control_fsm. Registering those flags (design iteration b) is what took WNS from +0.332 to +0.742 ns.
- Stage 2 combinational: three 3-input adders, one per window row: row_sum[0] = a+b+c, row_sum[1] = d+e+f, row_sum[2] = g+h+i. Each 18-bit signed (ROW_W = PROD_W + 2), range -97920..+97155.
- Why row-wise 3+3 rather than one 9-input sum: the grouping matches the window rows (same a-b-c / d-e-f / g-h-i structure as the taps and the masks), splits the 9-input sum into two 3-input adds in consecutive stages, and leaves stage 2 and 3 with large slack (+3.799 / +2.666 ns) so stage 1 alone is binding - the stages are balanced against the multiplier, which cannot be split further without touching the multiplier itself.
- Stage 2 register: row_r, 3 x 18 bits, plus v_row.
- Stage 3 combinational: acc = row_r[0] + row_r[1] + row_r[2], 20-bit signed (ACC_W = 20), range -293760..+291465, lossless; then saturate 20 -> 16 bits by the sign-extension check on acc[19:15] (details in section 7); then ReLU mux relu_out = (RELU && sat[15]) ? 0 : sat, where RELU is a build-time parameter (default 0) so the mux constant-folds away in the shipping build.
- Stage 3 register: pixel_out (16-bit signed) and valid_out.
- Register budget of the three stages: 144 + 54 + 16 data FFs plus 3 valid FFs; FFs do not appear in the FoM denominator, so full-width lossless intermediates cost nothing on the metric.
- Valid chain: win_valid (from control_fsm) -> v_prod -> v_row -> valid_out, one flip-flop per stage, level with the data registers; the pipeline registers have no enable, so the valid bit is the only thing that distinguishes a real result from a bubble.
- Stall behaviour: valid_in low -> en low -> taps and line buffers freeze -> win_valid low for that cycle -> a one-cycle bubble in valid_out exactly 3 cycles later; data already in the pipeline keeps advancing, so a stall can never corrupt an output. Regression asserts valid_out == win_valid delayed by exactly 3 every cycle (lat_err = 0) in all 22 runs; fixed-stall run: 16 stalls in STREAM, 16 bubbles observed.
- Latency accounting: 37 cycles from first accepted pixel to first valid_out = 34 window fill (FILL_CYCLES = LB_DEPTH 32 + 2 tap shifts) + 3 pipeline stages. Waveform: first valid_in at 145 ns, first valid_out at 515 ns, 370 ns = 37 cycles at the 10 ns TB clock.
- Throughput: one new window and 9 multiplies per enabled cycle, 1.0 output pixel per cycle peak, gapless within STREAM; 1024 outputs in 1061 cycles = 0.965 sustained per frame including fill and drain.
- Per-stage worst slack (routed, 8.000 ns, fpga/reports/paths.rpt): stage 1 window/coeffs -> prod_r +0.742 ns; stage 2 prod_r -> row_r +3.799 ns; stage 3 row_r -> pixel_out +2.666 ns. Stage 1 binds; stage 3 has 1.924 ns and stage 2 3.057 ns of headroom over it.
- Critical path: u_cu/bottom_edge_reg -> tap zero mux -> multiplier -> prod_r[8][13], 7 logic levels (4 CARRY4, LUT6, LUT5, LUT3), 7.297 ns, 59% routing; bottom_edge fanout 156 and 1.517 ns spent on that one net. Fmax = 1000/(8.000 - 0.742) = 137.8 MHz.
- All 15 worst paths start at an edge-flag register (bottom_edge_reg, top_edge_reg, right_edge_reg) and end in prod_r[8], [6], [2] or [5] - taps i, g, c, f, the ones masked by two flags or by the right flag - i.e. the limit is when the masks arrive at the multipliers, not the multiplier arithmetic itself.
- Known but not done: replicating the edge-flag registers per tap row to cut the fanout-156 net (est. 0.5-1 ns); timing already closes and Fmax is not in the FoM.
- Constant-coefficient multipliers (all real kernels are 0, +-1, +-2, +-4, 5) would cut roughly 300 LUTs but forfeit the mandatory programmability of spec item 3 - rejected; cross-reference the tradeoffs section.

## 7. Fixed-point bit-width analysis
**Required by:** Spec item 2 "Input precision: fixed point unsigned. Teams must justify the chosen precision in the report"; spec item 4 "Kernel precision: 8-bit signed fixed-point or integer"; spec item 6 "Output precision: minimum 16-bit signed. Teams must explain how overflow, truncation, saturation, or rounding is handled"; deliverable "fixed-point bit-width analysis"; Table 1 rows "Input precision", "Kernel precision".
**Say:**
- (REQUIRED, spec item 2) Input precision justification: 8-bit unsigned, Q8.0, 0..255 - matches 8-bit grayscale sensors and 8-bit feature maps exactly, so the image enters with no quantisation; it is the narrowest width that carries the input losslessly; Q8.0 (no fractional bits) needs no scaling or normalisation logic; unsigned because intensities are non-negative, so no bit is spent on a sign - the sign only appears after multiplication by a signed coefficient (the pixel is zero-extended to 9-bit signed inside mult8x8 for that multiply).
- Kernel precision: 8-bit signed two's complement, Q8.0 integer, -128..+127, exactly spec item 4. The five real kernels use only 0, +-1, +-2, +-4, 5, but every width below is sized for the full -128..+127 because the port is programmable (spec item 3) and any coefficient may be loaded.
- COEF_FRAC in rtl/cnn_pkg.sv: 0 = Q8.0 integer coefficients (the shipping build, all results in this report); 7 = Q1.7 rebuild intended for normalised blur/Gaussian kernels. At COEF_FRAC = 0 there is no shifter or rounder anywhere in the netlist.
- Widths are derived, not chosen: each intermediate is exactly the width that holds the full range of its stage for any 8-bit pixels and any 8-bit signed coefficients - no intermediate is ever truncated.
- Product: 8u x 8s, extreme values 255 x -128 = -32640 and 255 x 127 = +32385 -> 16-bit signed (PROD_W = IN_W + COEF_W = 16; 16-bit signed holds -32768..+32767).
- Row sum of 3 products: -97920..+97155 -> 18-bit signed (ROW_W = PROD_W + 2); 17-bit signed tops out at +-65535/65536 and would overflow.
- Accumulator, sum of 9 products (= 3 row sums): -293760..+291465 -> 20-bit signed (ACC_W = 20), lossless.
- Why ACC_W is exactly 20: the worst-case magnitude 9 x 255 x 128 = 293760 lies between 2^18 = 262144 and 2^19 = 524288, so 19 signed bits (max magnitude 2^18) are insufficient and 20 are sufficient; 21 or 22 would add flip-flops and carry length without adding information (an early 22-bit guess in older notes is superseded, docs/ARCHITECTURE_LOCKED.md section 3).
- Output: 16-bit signed, -32768..+32767, the spec minimum met exactly; the only narrowing in the whole datapath is 20 -> 16 bits at this point.
- (REQUIRED, spec item 6) Overflow: cannot occur inside the datapath, because every intermediate width is lossless through the accumulator; the only place a value can exceed its container is the 20 -> 16-bit output narrowing, and that is handled by saturation (clamp to -32768 / +32767), never by wrap-around.
- (REQUIRED, spec item 6) Saturation mechanism (rtl/top.sv lines 143-153): a 20-bit signed value fits in 16 bits exactly when its top five bits acc[19:15] are all copies of the sign bit, i.e. all 0 or all 1. fits -> pixel = acc[15:0]; not fits and acc[19] = 1 -> -32768 (OUT_MIN); not fits and acc[19] = 0 -> +32767 (OUT_MAX).
- Why the top-bits check equals two magnitude compares: acc > +32767 exactly when acc is non-negative and at least one of bits 19..15 is 1 (i.e. acc >= 2^15), and acc < -32768 exactly when acc is negative and at least one of bits 19..15 is 0 (i.e. acc < -2^15); the all-zeros / all-ones test on 5 bits captures both cases in about 2 LUTs instead of two 20-bit carry-chain comparators (design iteration c).
- Proof of equivalence: exhaustively checked in Python against max(-32768, min(32767, acc)) for all 2^20 = 1,048,576 accumulator values, 0 mismatches (docs/DESIGN_ITERATIONS.md section 3).
- Exercised in RTL: satmax (all nine coefficients +127) and satmin (all -128) kernels were added to the golden model specifically because no real kernel ever reaches the clamp; the golden model reports satmax output range [32767, 32767] and satmin [-32768, -32768], i.e. every one of the 1024 outputs of each, including the zero-padded borders, takes the clamp branch; hw_out/satmax_out.hex and hw_out/satmin_out.hex are byte-identical to golden, in clean, fixed-stall and random-stall runs, RELU=0 and RELU=1.
- Measured accumulator ranges on the 32x32 test image (golden_model/golden.py "acc range" printout): identity 41..255, sobel_x -715..+875, sobel_y -898..+934, sharpen -169..+557, laplacian -357..+241. The widest, sobel_y at 934, needs only 11 signed bits.
- Contrast: the datapath is sized for -293760..+291465, roughly 300x wider than any real kernel produces; the widths are set by the programmability requirement, not by the shipping kernels, and this gap is exactly why the saturation branches had to be covered by synthetic kernels.
- (REQUIRED, spec item 6) Truncation and rounding: none anywhere. All arithmetic is integer - Q8.0 x Q8.0 products, integer row sums, integer accumulator - so there are no fractional bits to drop and no rounding decision to make; the output is the exact integer convolution result whenever |acc| <= 32767 and the clamped value otherwise. State this explicitly as the answer to the "truncation or rounding" part of spec item 6.
- Zero padding costs no precision: masked taps are forced to 0 before the multiply, giving exact zero products, so border outputs are exact same-convolution results.
- ReLU (RELU = 1 build): negative saturated values -> 0 by a sign-bit test after saturation, so -32768 clamps first and is then zeroed; output range becomes 0..+32767, width unchanged at 16 bits.
- Golden model uses the same arithmetic: Python unbounded-integer accumulate, then clamp to [-32768, +32767], optional ReLU - 14 hw_out files x 1024 outputs bit-exact against it.
- Q1.7 rebuild (COEF_FRAC = 7) would require a right shift by 7 at the accumulator output with a rounding choice; only the Q8.0 build was synthesised, implemented and verified.
- Cost of full-width intermediates: 144 + 54 + 16 pipeline data FFs; FFs are not in the FoM denominator (LUTs + 50 x DSPs + 100 x BRAMs), so lossless widths are free on the metric and cheaper in LUTs than any intermediate rounding logic would be.

## 4. FSM state diagram
**Required by:** Deliverable "FSM state diagram"; Instruction 1 "clearly describe the ... control FSM"; Instruction 4 "state all assumptions clearly" (no-ready frame contract); judged under "digital design quality" and "latency".
**Say:**
- control_fsm (rtl/control_unit.sv) is the only block that knows the frame position: window_gen has no counters, the datapath has no position state. From valid_in alone it drives en, the four registered edge flags (top/bottom/left/right_edge), win_valid, busy and frame_done. frame_done is internal to top, not one of the 42 pins.
- Five states, 3-bit enum S_IDLE, S_FILL, S_STREAM, S_DRAIN, S_DONE; Vivado one-hot encodes it. Routed hierarchy (fpga/reports/utilization_hier.rpt, indicative): u_cu = 80 LUTs, 35 FFs = 5 state + 10 in_cnt + 5 out_r + 5 out_c + 6 drain_cnt + 4 edge flags.
- Transitions: IDLE -> FILL on valid_in; FILL -> STREAM on valid_in && in_cnt == 33 (FILL_CYCLES-1); STREAM -> DRAIN on last_consume = consume && in_cnt == 1023 (NPIX-1); DRAIN -> DONE on drain_cnt == 33 (DRAIN_CYCLES-1); DONE -> IDLE unconditionally after exactly 1 cycle.
- Output equations: en = valid_in in IDLE/FILL/STREAM, forced 1 in DRAIN, 0 in DONE; consume = en && state != DRAIN; out_adv = en && (state == STREAM || state == DRAIN); win_valid = out_adv; busy = (state != IDLE) && (state != DONE); frame_done = (state == DONE).
- IDLE is not a dead cycle: en = valid_in there too, so the first pixel is consumed on the IDLE -> FILL transition itself (in_cnt 0 -> 1, LB0 shifts). busy therefore rises one cycle after the first accepted pixel.
- (REQUIRED, latency) Frame bookkeeping in enabled cycles: 34 consume-only (1 in IDLE + 33 in FILL, in_cnt 0..33) -> 990 consume+output in STREAM (in_cnt 34..1023, output positions (0,0)..(30,29)) -> 34 output-only in DRAIN (drain_cnt 0..33, positions (30,30)..(31,31)) -> 1 DONE cycle. Consumes 34 + 990 = 1024, outputs 990 + 34 = 1024.
- FILL = DRAIN = 34 is forced, not chosen: every enabled cycle is consume-only, consume+output, or output-only; consumes must total 1024 and outputs must total 1024, so output-only cycles == consume-only cycles. cnn_pkg.sv defines DRAIN_CYCLES = FILL_CYCLES for exactly this reason.
- Why 34: line-buffer depth 32 + 2 tap shifts (LB0 output -> tap f -> tap e). Only LB0 sits between the input and the centre tap; LB1 feeds the top row, which is zero-masked on row 0, so it does not gate the first output. (Cross-reference the window-generation section.)
- Why DRAIN with en forced high is safe: output (31,31) needs 34 + 1024 - 1 = 1057 shifts but only 1024 real pixels exist; the 33 extra shifts push whatever is on input_in into the bottom tap row (the TB drives 0xA5 during drain), and every window that sees it is bottom_edge- or right_edge-masked, so nothing leaks into any output.
- Whole-frame numbers that follow: latency 37 cycles = 34 window fill + 3 pipeline stages (latency.PNG: 145 ns -> 515 ns = 370 ns at the 10 ns TB clock); frame span 1061 cycles first valid_in to last valid_out = 34 + 990 + 34 + 3; throughput 1.0 output/cycle peak, gapless in-frame, 1024/1061 = 0.965 sustained.
- Counters and widths: in_cnt 10 b (0..1023, increments on consume, wraps to 0 on the last consume); out_c 5 b and out_r 5 b (advance on out_adv through nxt_c/nxt_r, 31 wraps to 0); drain_cnt 6 b (counts only in DRAIN, held at 0 elsewhere). Synchronous active-low reset puts state IDLE, every counter 0, flags at position (0,0).
- in_cnt is not redundant (docs/DESIGN_ITERATIONS.md, item 1): consume also runs during FILL, so the input count leads the output position by exactly 34; at the last consume the output position is (30,29), not a corner, so bottom_edge && right_edge cannot replace the in_cnt == 1023 trigger. The substitution was modelled and gave 1059 consumed / 1058 out instead of 1024 / 1024; reverted.
- Edge flags are four FFs inside the FSM: reset to top=1, left=1, bottom=0, right=0 (position (0,0)); every cycle they are registered from nxt_r/nxt_c, which is the position after the current one when out_adv is high and the current position otherwise. top = (nxt_r == 0), bottom = (nxt_r == 31), left = (nxt_c == 0), right = (nxt_c == 31). On the cycle a window sits at the taps its flags are already in flip-flops.
- (REQUIRED, critical path) Why they are registered: the baseline critical path was u_cu/out_c_reg[4] -> right_edge comparator -> tap zero mux -> multiplier -> prod_r[8][13], 8 logic levels, 7.633 ns, 62% routing, comparator net fanout 127, WNS +0.332 ns. After registering: u_cu/bottom_edge_reg -> tap zero mux -> multiplier -> prod_r[8][13], 7 levels (4 CARRY4, LUT6, LUT5, LUT3), 7.297 ns, 59% routing; WNS +0.332 -> +0.742 ns, Fmax 130.4 -> 137.8 MHz.
- Cost of registering: 4 FFs (441 total, from 437); LUTs 882 -> 879, i.e. flat - the comparator logic moved out of the multiplier cycle, it did not shrink. Latency, throughput and the module interface unchanged.
- What is left on the path: bottom_edge fanout 156, 1.517 ns of the 7.297 ns is that one net into window_gen; all 15 worst paths start at an edge-flag register and end in prod_r (bottom_edge -> prod_r[8] and prod_r[6] 10 of 15, top_edge -> prod_r[2][*] 4, right_edge -> prod_r[5][13] 1). Replicating the flag registers per tap row (about 8 FFs, est. 0.5-1 ns) was identified and not done - timing closes, and Fmax is not in the FoM.
- Flags verified: tb_top_window checks out_r/out_c and all four flags against the expected raster position on every one of the 1024 windows - 0 position/edge errors, fill latency 34, 0 gaps in win_valid.
- Stall in FILL (or IDLE): en = 0 freezes LB0, LB1, the taps and in_cnt; out_adv is already 0, so the only effect is that the first valid_out moves later by the stall length. Fixed-stall run: 2 cycles before pixel 10, no bubble.
- Stall in STREAM: en = 0 freezes the window, in_cnt, out_r/out_c and the flags (nxt = current when out_adv = 0) and drops win_valid; the three pipeline registers are free-running with a valid bit travelling alongside the data, so the identical gap appears in valid_out exactly 3 cycles later - a bubble, never a corrupted or duplicated pixel (stall.PNG: 3 cycles before pixel 300).
- Stall in DRAIN: impossible by construction - en is forced 1, consume is 0, valid_in is ignored; DRAIN always takes exactly 34 cycles, so the frame tail (frame_done, busy falling) is deterministic relative to the last accepted pixel. In DONE en = 0.
- Regression evidence for stalls (tb/tb_top_all.sv, 22/22 runs pass): fixed stalls before pixels 10 (2 cycles), 300 (3), 511 (1, row boundary), 700 (8), 1023 (4) = 18 cycles, 16 in STREAM, 16 bubbles observed; random stalls hold about 1 in 5 pixels for 1-4 cycles, roughly 500 stall cycles per run, bubbles always equal to STREAM stalls; every cycle valid_out must equal win_valid delayed by exactly 3 (lat_err = 0), checked on both the RELU=0 and RELU=1 DUTs.
- (REQUIRED, assumption) Frame-to-frame contract: there is no ready signal in either direction. The source streams exactly 1024 pixels per frame and holds the next frame until busy falls; the sink must accept every valid_out. Pixels driven during DRAIN would be shifted in (en = 1) but never counted, so they would be lost - hence wait for busy.
- busy falls when the FSM enters DONE, 3 cycles before the final valid_out: the last window has already been multiplied into prod_r and the last three outputs are in the adder / saturate stages. The TB's finish_frame waits for !busy and then 8 more cycles (drain.PNG).
- (assumption) A pixel presented in the single DONE cycle is not consumed (en = 0); the first pixel of the next frame must arrive no earlier than the following IDLE cycle. A source that registers busy before reacting satisfies this automatically.
- Coefficient write lock (rtl/coeff_reg.sv): a write lands only when write_en && !busy && write_addr < 9; writes during FILL, STREAM or DRAIN are silently dropped, writes in IDLE and DONE are accepted. Consequence: every output of a frame is computed with one kernel (kernel_load.PNG: 9 writes with busy low).
- Back-to-back proof (tb_top_all run "sobel_x -> sharpen, back to back"): frame 1 streamed, wait(!busy), sharpen's 9 coefficients written immediately while frame 1's last three outputs are still leaving the pipeline, frame 2 streamed with no idle gap; 2048 outputs, all match their golden files on both DUTs. Safe because coefficients feed only stage 1 and the last window has already been multiplied when busy drops.
- frame_done is a one-cycle pulse in DONE, coincident with busy low; tb_top_window uses it to end the frame. The per-state values of all outputs are in the state/output table.

- Do not call busy a ready or handshake signal; there is no backpressure on either side, and the sink must accept every valid_out.
- Do not claim stalls are tolerated in DRAIN or that valid_in has any meaning there.
- Do not draw or describe the edge flags as combinational decodes of out_r/out_c (the old drawing) - they are FSM registers.
- Do not claim registering the flags saved area: 882 -> 879 LUTs is flat; the gain was WNS +0.332 -> +0.742 ns and Fmax 130.4 -> 137.8 MHz. Do not fold 137.8 MHz into the FoM (FoM is at 125 MHz).
- Do not claim edge-flag replication was done, or a board demo.
- Do not present 80 LUTs / 35 FFs for control_fsm as exact - hierarchical numbers are indicative because Vivado merges LUTs across boundaries; 879 / 441 is the number.
- Do not describe frame_done as a pin; the 42 pins are clk, rst_n, 8 input_in, valid_in, 13 write-port, 16 pixel_out, valid_out, busy.
- Do not say the kernel can be changed mid-frame; writes are dropped while busy and the back-to-back swap happens after busy falls.

- multiplier.sv, `module mult8x8`, ports coef signed[7:0], pix[7:0], prod signed[15:0], 7 lines: `assign prod = coef * signed'({1'b0, pix})` - the unsigned pixel is zero-extended to a 9-bit signed operand so the product is a true signed 8 x 9 multiply (synth.log RTL Component Statistics: "8x9 Multipliers := 9"); carries `(* use_dsp = "no" *)`, the only vendor-specific line in the RTL; 52-59 LUTs each, 496 in total, 0 DSP.
- coeff_reg.sv, `module coeff_reg`, ports clk, rst_n, write_addr[3:0], data_write[7:0], write_en, busy, coef_out[0:8][7:0]:
  - storage coef_reg[0:8], 72 FFs; write guard `write_en && !busy && write_addr < NTAP` - a write during FILL/STREAM/DRAIN is ignored so a kernel can never change under a frame, and the unused addresses 9..15 of the 4-bit port are dropped instead of aliasing.
  - reset clears all nine coefficients to 0; write_addr = 3*row + col, the same row-major order as the taps.
  - the 120 LUTs are the address decoder and nine byte-wide enables, not the storage; the write port shape (addr + data + enable) is part of the documented interface and was kept.
  - the guard is timed to the pipeline: busy falls when the last window's products are already in prod_r, so a rewrite the cycle busy drops cannot touch frame 1 - exercised by the back-to-back run in tb_top_all (sobel_x then sharpen, `wait(!busy); load("sharpen")`, 2048 outputs correct).

## 10. Golden model
**Required by:** spec item 8 ("golden reference model implemented in Python, MATLAB, or C"); deliverables "golden model", "input test images", "expected output files"; supports spec item 6 (evidence that saturation is handled as explained).
**Say:**

- conv(img, k, relu): for every output (y, x) in 0..31: acc = sum over dy, dx in {-1, 0, 1} of img[y+dy, x+dx] * k[dy+1, dx+1], taps that fall outside the image are skipped - that is zero padding, "same" convolution, 1024 outputs per frame; then acc = max(-32768, min(32767, acc)) - the clamp that defines the required saturation behaviour; if relu and acc < 0 then 0 - ReLU after saturation, the same order as the RTL (saturate, then the ReLU mux).
- Kernel orientation (state as an assumption): k[row][col] is applied unflipped to the window, i.e. cross-correlation, the usual CNN convention; identical to the RTL, which multiplies tap[n] by coef[n] with tap[0] = top-left of the window and write_addr = 3*row + col.
- Input image: golden_model/cat.png -> PIL convert("L") -> resize to 32x32 -> uint8 -> hex/image.hex (1024 lines, %02x, one pixel per line, raster order); the pixel values in the shipped file span 41..255.

## 15. Discussion of design tradeoffs
**Required by:** deliverable "discussion of design tradeoffs"; judging on "digital design quality, FPGA resource usage, latency, throughput, timing closure, and power estimate"; FoM definition (requirement 10).
**Say:**
- Frame every choice against the one equation: FoM = Throughput / (Power x (LUTs + 50 x DSPs + 100 x BRAMs)); with DSP = BRAM = 0 the denominator is 0.158 W x 879 LUTs = 138.9, and every tradeoff below was judged on that product *after* the mandatory specs were satisfied, never instead of them.
- **9 parallel MACs vs 3 vs 1** (throughput vs area):
  - chosen: 9 multipliers, all 9 taps consumed every clock, 1.0 output pixel/cycle peak, 0.965 sustained per frame (1024 outputs in 1061 cycles) - this is what earns the one-output-pixel-per-cycle bonus.
  - cost: 496 of 879 LUTs (56%) are the nine multipliers, 52-59 LUTs each.
  - 3-MAC alternative (one row per cycle): throughput 1/3 px/cycle; removes 6 multipliers = roughly 312-354 LUTs (estimate from the 52-59 LUTs/multiplier figure, not synthesised) but window_gen (132), control_fsm (80), coeff_reg (120) and the adder/saturate glue (90) stay, so the denominator falls to only about 0.6x while the numerator falls 3x - FoM roughly halves.
  - 1-MAC: 1/9 px/cycle, needs a 9-step sequencer and accumulator on top; same arithmetic, roughly 4-5x worse FoM (estimate).
  - point to make: throughput is the only term in the numerator and the frame machinery is a fixed cost, so full parallelism wins on the metric as well as on the bonus.
- **LUT multipliers vs DSP48 (the x50 arithmetic)** (REQUIRED - FPGA resource usage):
  - one DSP counts as 50 LUT-equivalents; a measured 8u x 8s LUT multiplier is 52-59 LUTs; 9 DSPs = 450 units vs the 496 LUTs actually used - a difference of 46 units, about 5% of the 879 denominator, so nearly a wash.
  - LUTs chosen at architecture lock (docs/ARCHITECTURE_LOCKED.md §1): denominator becomes a single measured term (LUTs only), RTL stays vendor-neutral (one attribute use_dsp="no" plus -max_dsp 0 at synthesis), and an 8x8 product is small enough that the LUT version still closes with +0.742 ns at 125 MHz.
  - be candid that the x50 weight is evidently calibrated to make a small multiplier cost about the same either way; this was not a large FoM win, it was a simplicity/portability decision.
- **Line buffers: SRL vs FF vs BRAM (the x100 arithmetic)**:
  - the delay is 2 x 32 x 8 = 512 bits; one BRAM would be 100 denominator units (200 if one per line) against the 16 LUTs Vivado actually used (16 SRLC32E, 0 BRAM): a BRAM would have added 84-184 units to 879, i.e. 10-21% worse FoM, to hold 512 bits in an 18/36 kbit block.
  - Vivado inferred the SRLs despite the synchronous reset because only sr[DEPTH-1] is ever read; 16 LUTs instead of 512 FFs; "LUT as Shift Register = 16" in fpga/reports/utilization.rpt is the expected, good outcome.
- **Same (zero-padded) vs valid convolution**:
  - same: 1024 outputs per 1024 inputs, valid_out gapless for the whole frame, 32x32 in -> 32x32 out as a CNN layer expects; valid: 30x30 = 900 outputs and valid_out drops for 2 cycles at every row boundary, which forfeits the *sustained* (not peak) 1 px/cycle claim.
  - price paid: 4 edge flags and 24 tap zero-muxes (top->0,1,2; bottom->6,7,8; left->0,3,6; right->2,5,8) sit in front of the multipliers - all 15 worst timing paths start at an edge-flag register, so the border logic cost timing headroom, not LUTs or throughput.
- **Registered edge flags (iteration b)** - before/after path:
  - before: u_cu/out_c_reg[4] -> right_edge -> tap zero mux -> multiplier -> prod_r[8][13], 8 logic levels (4 CARRY4, 2 LUT6, LUT5, LUT4), 7.633 ns, 62% routing; WNS +0.332 ns, Fmax 130.4 MHz.
  - after: u_cu/bottom_edge_reg -> tap zero mux -> multiplier -> prod_r[8][13], 7 levels (4 CARRY4, LUT6, LUT5, LUT3), 7.297 ns, 59% routing; WNS +0.742 ns, Fmax 137.8 MHz (+5.6%).
  - cost: +4 FFs (437 -> 441), LUTs 882 -> 879 (the logic moved, it did not grow); latency, throughput and interface unchanged; flags are computed one position ahead (nxt_r / nxt_c) so they are valid on the cycle they are used.
  - what is left is fanout, not logic: bottom_edge drives 156 loads and 1.517 ns of the 7.297 ns path is that single net into window_gen.
- **Saturation rewrite (iteration c)** - why it is kept although it bought no timing:
  - two 20-bit signed compares (acc > 32767, acc < -32768) replaced by one 5-bit all-equal test on acc[19:15], clamp by the sign bit when it fails; about 2 LUTs cheaper; proven equivalent over all 2^20 accumulator values in Python (0 mismatches).
  - bought no timing: stage 3 worst slack +2.666 ns vs stage 1 +0.742 ns, 1.92 ns headroom - the saturate stage was never the constraint (report_timing_summary only prints the single worst path, so this was not knowable before fpga/paths.tcl was written).
  - kept because it is cheaper, proven, and writing it exposed that no real kernel ever reaches the clamp (widest is sobel_y, -898..+934), so both clamp branches had been untested -> satmax (all +127) and satmin (all -128) added, regression 16 -> 22 runs; the verification gap is the real outcome.
- **The in_cnt removal that failed (iteration a)** - present as engineering rigour:
  - idea: in_cnt (10-bit) only feeds last_consume = consume && in_cnt == 1023, and out_r/out_c already count the frame, so STREAM -> DRAIN could reuse bottom_edge && right_edge and drop the counter plus its 10-bit comparator.
  - why it is wrong: consume is asserted during FILL as well as STREAM, so inputs lead outputs by exactly 34 positions; at the last consumed pixel the output position is (30, 29) - not a corner, not expressible by the edge flags.
  - caught by modelling the modified FSM in Python before touching RTL: 1059 consumed / 1058 output instead of 1024 / 1024; reverted; never reached RTL or the regression.
  - the workable variant out_r == 30 && out_c == 29 was also rejected: two 5-bit compares for one 10-bit compare, and it silently breaks if FILL_CYCLES ever changes.
  - what the exercise established: the baseline 165 LUTs in control_fsm were not a redundant counter but the four edge comparators (each driving 24 tap muxes), the en/consume/out_adv fanout and a replicated one-hot state register - which is exactly the work that iteration (b) moved (control_fsm 165 -> 80, indicative).
- **SAIF-annotated vs vectorless power (iteration d)**:
  - vectorless (Vivado default 12.5% toggle, Low confidence): 0.181 W total, 0.074 W dynamic; SAIF-annotated: 0.158 W total, 0.052 W dynamic, static 0.107 W in both, Medium confidence.
  - FoM 6.285e-3 -> 7.20e-3, +14.6%, with zero RTL change - the largest single FoM gain in the project came from measuring properly, not from design.
  - 414 of 2229 design nets annotated (19%) is a naming ceiling: the unmatched nets are synthesis-invented LUT-to-LUT nets no RTL simulation can name; the matched ones are the I/O, taps, products, accumulator and pipeline registers - the high-activity nets; High confidence would need post-implementation timing simulation with a netlist-level testbench, which was not asked for.
- **Constant-coefficient multipliers rejected**:
  - every shipping kernel uses only 0, +-1, +-2, +-4, 5; hard-coding them collapses the multipliers to shifts and adds and would cut roughly 300 LUTs.
  - rejected because requirement 3 makes coefficient programmability mandatory, and trading a mandatory spec for a tiebreaker metric is the wrong trade; the datapath widths (16b products, 18b row sums, 20b accumulator, saturation) are sized for any 8-bit signed coefficients for the same reason.
- **Where the power actually goes and what it means for further work** (REQUIRED - power estimate):
  - 0.158 W = static 0.107 (68%) + I/O 0.042 (27%) + clocks 0.004 + slice logic 0.003 + signals 0.003 (the design's own logic, about 6%).
  - every RTL iteration above moved only that 6%; static power is a property of the xc7z020 die, and the I/O share is an artefact of exposing all 42 core ports on LVCMOS33 pads (inside a real system these signals stay on-chip and the dynamic figure would be a fraction of this).
  - so the remaining levers are the device (ruled out: PYNQ-Z2 is the required board) and the I/O standard / drive strength of the 42 pads - not the RTL.
- **FoM frequency: 125 MHz, not Fmax** (REQUIRED - organiser asked for the frequency used):
  - throughput in the formula is per cycle and therefore clock-independent; dynamic power scales roughly linearly with clock; so a higher clock only lowers the FoM.
  - 125 MHz is the constraint the design was implemented and verified against, the board's clock on H16, and the clock the SAIF represents - power and frequency are self-consistent; going below the board clock would read as gaming the metric; the organiser left the choice to the team.
  - Fmax 137.8 MHz is reported under timing closure only and is deliberately not folded into the FoM.
- **Identified and quantified, not done**:
  - replicate the edge-flag registers per tap row (max_fanout or explicit dont_touch duplicates): about 8 FFs, free in the FoM, est. 0.5-1 ns off the fanout-156 net; not done because timing closes, Fmax is not in the FoM, and the gain is routing-dependent rather than structural.
  - DRIVE 4 on the outputs (pixel_out, valid_out, busy): est. ~10% of total power; not done - by decision no experiments were run on the frozen submission build once the numbers were reproduced on 13 Sep.
  - any other device: static 0.107 W (68% of the power term) would fall on a smaller die; not done - PYNQ-Z2 is a hard requirement.
  - coeff_reg at 120 LUTs is mostly the 4-bit write-address decoder fanning out to 9 byte-wide enables; a shift-in chain would shrink it, but the addressed write port is the documented interface (fpga/reports/RESULTS.md).
- Reproducibility as a quality claim: 879 / 441 / 0 / 0, WNS +0.742 / WHS +0.153, 0.158 W, FoM 7.20e-3 obtained identically by two different flows two days apart (11 Sep in-memory Tcl flow, 13 Sep project flow); post-synthesis 910 LUTs is an estimate before opt_design / LUT packing and is not the number.
